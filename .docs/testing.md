## 两套 suite

两套 suite，各自独立的配置和生命周期。

**单测** —— `vitest.config.ts`，`tests/` 下直接的文件，由 `pnpm test`（`vitest run`）跑。全部是纯函数与临时目录级别的断言，不 fork 进程。`tests/utils.test.ts` 覆盖 `src/utils.ts` 的 12 个导出，`tests/constants.test.ts` 钉住模板注册表。这份配置**显式排除了 `tests/e2e/**`**——`*.e2e.test.ts` 同样匹配 include 里的 `*.test.ts`，不排掉的话每次 pre-commit 都会连 E2E 一起跑。

**E2E** —— `vitest.e2e.config.ts`，只收 `tests/e2e/**/*.e2e.test.ts`（后缀限定，所以 `tests/e2e/helpers` 下的文件不会被当成用例），由 `pnpm test:e2e` 跑。它真的 fork `node bin/index.js` 到临时目录，对真实产物断言。不进 pre-commit，改为进 `build:prod` 和两个 workflow 的门禁。

写 E2E 用例前必须知道的几件事：

- **CTV-31 之后，非交互路径会打印一句人话**。此前它一个字都不打（clack 的 promise 永不 settle），所以那时候的注释写着「不要断言任何提示文案」——那句话现在**已经失效**，`cli-basics` 与 `target-path` 里的相关注释都已改写。提示文案本身由 `non-interactive.e2e.test.ts` 专门钉住，其余文件只管退出码与副作用，两边刻意不重叠。
- **断言提示文案时全部硬编码，不从 `src/` import 常量派生**。期望值一旦和实际值同源，断言就退化成恒等式（CTV-30 已用变异实测证实过一次）。
- **非交互三件套是 `-t <模板> --overwrite --no-immediate`。** `--no-immediate` 不可省：不给它 CLI 会停在「是否立即安装依赖」的确认框上；而 `-i` 会**真的联网跑 npm install**。mri 把 `--no-immediate` 解析成 `immediate: false`，于是走打印后续步骤的分支，既不提问也不联网。**任何 E2E 用例都不该触发真实安装。**
- **子进程的环境是白名单，不是当前进程的环境**（`helpers/cli.ts`）。最要紧的是 `npm_config_user_agent`——它决定 `pkgFromUserAgent()` 认出哪个包管理器，进而影响收尾提示里的安装命令。跑测试的人用 pnpm 还是 npm，不该改变断言结果。
- **给共享状态写断言时用绝对值，别用「操作前后相等」**——状态已被同文件其它用例弄脏时，后者会一路绿着骗人（第三方库就地改写模块级常量的那类污染，就是这么被瞒过去的）。
- **永远不要在测试里调 `process.chdir()`**，vitest 的 worker 共享进程。cwd 是传给子进程的。
- **`globalSetup` 会先构建 `dist/`**，所以用例不可能对着过期产物断言。这一步放在 globalSetup 而非 `pnpm build && vitest run` 的脚本串里，是因为前者同样覆盖「从 IDE 单跑一个文件」和 `--watch`。`E2E_SKIP_BUILD=1` 可跳过（要求 dist 已存在）。
- **失败的 fixture 会被保留并打印路径**，`E2E_KEEP=1` 则一律保留。
- **`fixture.tree()` 刻意不列 `.git`**（CTV-22）。它是 git 的内部状态而不是项目文件树，列进来会让每条 `toEqual` 多出几十行，且那些内容随 git 版本变化（hooks 样例数量、objects 布局），换台机器就可能红。仓库是否被初始化改由 `git-init.e2e.test.ts` 用 `exists('<项目>/.git')` 专门钉住，两边刻意不重叠。**加这条排除时既有 91 条一条都没变**，因为那之前 fixture 里根本不会出现 `.git`。
- **`runCli()` 返回两份 stdout**：`stdout` 剥掉了 ANSI（断言文本用它），`stdoutRaw` 没剥（断言转义序列用它，比如光标）。拿 `stdout` 去断言光标永远是空。
- **断言框线时看「最后一行非空输出」，别去数 `└` 的个数**——画到一半的 select 菜单自己会渲染一行光秃秃的 `└`，正常输出就能数出 2 个。有收尾语的路径要**整行相等**：`outro('')` 渲染成 `└  `，只判 `/^└/` 的话「收尾语丢了」照样全绿（变异实测过）。

**曾经的留白已经补上一半**（CTV-34，2026-09-08）。helper 的 `stubPackageManager: true` 会在 PATH 最前面放一个立刻成功返回的假包管理器——`install()` 和 `customCommand` 都靠 `cross-spawn` 按 PATH 解析命令名，所以这两条路径现在能离线跑完。

边界要说清楚：**它测的不是包管理器能不能干活**（那是 npm 的事），而是「我们把命令发出去之后，自己这边的收尾渲染对不对」。真实联网安装、以及上游脚手架真的生成了什么，仍然不在 E2E 覆盖内。

`stubPackageManager` 传对象可以指定退出码（`{ exitCode: 7 }`），用来覆盖**安装失败**那一支（CTV-39）。**挑退出码时避开 1**：那个值和「取消」「参数有误」撞车，透传测试会分不清退出码到底是包管理器给的还是我们自己兜出来的。

**仍然没有被覆盖的**：真实联网安装本身、以及上游脚手架真的生成了什么。

## 四条验证标准 · 证据留档

下面是这四条标准在 [CLAUDE.md](../CLAUDE.md) 被压缩成禁令之前的原文，实测数字与来龙去脉都在这里。
模板那一条的展开见 [templates.md](./templates.md)，发布产物那一条见 [release.md](./release.md)。

- **表征测试必须用变异证明断言有牙齿。** 给存量代码补的测试天然一次就绿，那说明不了任何事。做法是往源码里逐个注入真实缺陷，确认每个都能让某条断言转红，然后**还原源码并 diff 校验**。这个仓库做过两轮：`src/utils.ts` 13 个变异 13 个被捕获；E2E 9 个变异 8 个被捕获，第 9 个经核实是等价变异（不是盲区）。**报告时要说清哪些被捕获、漏掉的那个是不是等价变异**，不要凑数字。
- **断言的期望值不要从被测数据派生。** 2026-09-08（CTV-30）实测：给「第一层选择器只列框架」写的 E2E 断言，期望值写成 `FRAMEWORKS.map(f => f.display)`，看着很「防漂移」，实际是**弱断言**——改掉某个框架的 `display`，输出和期望会一起变，变异（`Vue` → `Vue.js`）全绿存活。派生只在「校验清单」类断言里对（如 `collectKnownFlags()` 从 `ARGV_OPTIONS` 派生，那里两边是不同的东西）；**当期望值和实际值来自同一个源，断言就退化成恒等式**。注册表的内容该由显式清单钉住——`constants.test.ts` 硬编码 `TEMPLATES` 数组就是对的做法。判据很简单：**问一句「改被测源码的哪一处能让这条断言变红」，答不上来就是恒等式。**

- **模板改动必须真装一次、真构建一次，而且 npm 与 pnpm 都要跑。** 2026-09-10 的全量验收
  一次性查出三个缺陷，**没有一个能靠读代码或跑现有 342 条自动化测试发现**：`pnpm install`
  退 1（只在 pnpm 下暴露）、`vue-tsc` 报 TS7016（两个包管理器都暴露，但要真构建）、开箱
  `pnpm lint` 退 1（要在**生成出来的项目里**用**模板自己的** eslint 跑，本仓库的 eslint
  忽略了 `template-*`，而且拿本仓库的 eslint 去 lint 模板会挂死）。单测里的静态断言只是
  这些不变量的**代理**，代理绿不等于事情对。

### 2026-09-21 · CTV-49：17 个变异 0 存活，外加两条「测试环境够不着」的留白

banner 这一批新写了 22 条断言（单测 14 + E2E 8），全部逐条变异验证过，**17 个变异 0 存活**：
`resolveBannerMode` 的两条判据各删一次、字标改宽不改阈值、纯文本模式也画字标、超链接分支
反转、版本行漏作者、版本号不链 npm、收尾不留空行、字标挪到开框之后 / 挪到 `--version` 之前 /
挪到参数校验之前 / 压根不打、版本号写死、作者写死、`getPkgMeta` 的三条回退路径各改一次、
子集字体裁掉 V、品牌名改成子集没覆盖的字母。每次改完还原源码并 `git diff --stat` 校验无残留。

**值得单独记的两条留白**——按第四条标准「判据超出测试环境能力时，不要假装测试覆盖了它」：

- **渐变着色量不出来。** gradient-string 底下是 chalk，chalk 在非 TTY 下 level 为 0，
  `gradient(...).multiline(x)` 原样返回 `x`。写过一条「字标上了渐变色」的断言，**它在
  vitest 里永远红、在 CI 里永远假绿**，删掉并在测试文件里写明理由。拿 `FORCE_COLOR`
  硬撑等于在测 chalk 而不是测自己的代码。
- **OSC 8 超链接在 E2E 里不可达。** `runCli` 的环境是 `TERM=dumb` + 管道，
  `terminalLink.isSupported` 必然为 false，只能覆盖「补明文 URL」那一支。
  另一支用 `FORCE_HYPERLINK=1` 在真实 pty 里手动验过（那是 supports-hyperlinks
  自己的环境开关，不是伪造），**没有自动化守卫**。

两条都在真实 pty 里补验过：120 列 → 渐变字标 `rgb(0,198,255)` → `rgb(163,77,255)`；
60 列 → 退化成加粗纯文本；`FORCE_HYPERLINK=1` → 版本号与作者挂上 OSC 8 且明文 URL 行消失。

**还暴露了一个流程缺陷**：变异脚本改的是 `src/`，而 E2E 跑的是 `dist/`。
跑完 pty 复验时字标下面赫然写着 `v1.10.0 - someone`——源码早还原了，**`dist/` 还留着
上一轮变异的产物**。以后变异验证之后、真跑之前必须重新 `pnpm build`。

- **发布产物必须实测，不能拿本地构建代替。** 见下面「Release · 发版清单」第 5 条。`files` 字段配错、npm 剔除 `.npmrc`/`.gitignore` 这类问题只在真实 tarball 里暴露。
